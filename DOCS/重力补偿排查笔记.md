# 重力补偿（A5b）排查笔记

## 已确认

1. **正运动学正确**：`App/cfg/gravity_model.h` 的 7 段与 pinocchio `oMi` 逐段对比，`dR/dp < 1.5e-9`。
2. 关节轴来自 URDF `<axis>`（不是全 z）。
3. 生成器 `Scripts/gen_gravity_model.py` 的链序从 `parents` 推导。

## 当前失败现象

用同一套（yaml 覆盖后的）参数，板端势能梯度与 pinocchio `rnea` 对比：

```
q = 随机位形
pinocchio: [-1.433  1.443  0.671  0.923 -0.225 -0.019  0.330]
model-U  : [-2.411 -0.636  0.462  0.912 -0.065 -0.441  0.012]
diff     : [-0.978 -2.079 -0.209 -0.011  0.160 -0.422 -0.318]
```

注意：**肘关节（idx 3）几乎吻合**（0.912 vs 0.923），近端（0/1）和远端（5/6）差得多。
→ 不是"框架整体错"，而是**个别连杆的惯性参数表达**不对。

## 下一步（按顺序）

1. **逐连杆隔离**：每次只保留一个连杆的 (mass, mc)，其余置零，分别算 pinocchio 与模型 U 的梯度，逐个对比 → 定位到具体连杆。
2. 重点怀疑：
   - yaml 的 `first_moment` 所在坐标系（标定链路系）与 pinocchio `inertias[jid]` 的关节系是否一致，
     若不一致需要乘 URDF 里该关节的固定旋转；
   - URDF 的 `<inertial><origin>` 是否有非零旋转/平移（当前生成器只用 yaml 的 com，忽略了它）；
   - fixed 子连杆（相机/夹爪指尖）被 pinocchio 合并进父连杆，覆盖惯量时被丢掉；
   - `mass: null` 的连杆（shoulder_pitch）按 0 处理，但它的 `m·c` 仍参与重力矩。
3. 修好后 `make test` 的 `max_err` 应 < 1e-3 N·m，再把 `GRAVITY_FF_ENABLE` 置 1。

## 最终采用方案（B）：rnea 采样 + 基函数拟合

之前复现 FK 的路子放弃（pinocchio 自身 rnea 与其势能梯度都对不上，说明有结构性约定没吃透）。
现在：

- `Scripts/fit_gravity.py`：用**和 `gravity_compensator.cpp` 完全相同**的模型注入方式（yaml 的
  mass/first_moment 写进 `model.inertias[jid]`），在 ±1.6 rad 内采样 5000 组，`rnea(q,0,0)` 求 τ；
- 基函数 379 项（常数 + 一阶 sin/cos + 二阶 4 组合 + 三阶 8 组合），最小二乘拟合
  每侧 7 关节 → `App/cfg/gravity_fit.h`（float 系数，21KB flash）；
- `App/control/gravity.c` 只做乘加（每侧 7×379 次）；
- `Tests/test_gravity.c`：300 组留出样本，**max_err ≈ 1.3 N·m**（|τ| 最大约 6 N·m），rms ≈ 0.3；
- `GRAVITY_FF_ENABLE` 已置 1，DRAG 模式输出重力前馈。

---

## 最终结论（精确解析式，取代方案 B）

方案 B 拟合误差 1.3 N·m 仍偏大；根因不是"pinocchio 约定没吃透"，而是
**参数注入/运动链建错**：

1. `mass: null` 的连杆被 `m=0` 处理，`mc` 也一起清零 → 丢掉肩 pitch 的
   `my/mz`（近端关节误差的主要来源）。
2. 旧生成器只取 7 个臂关节，**漏掉夹爪两段**（它们的一阶矩对腕/肘/肩都有贡献）。
3. 夹爪两根手指是 `wrist_pitch` 的**兄弟**，不是串联；按串行处理会算错远端集合。
4. 旧 `gen_gravity_model.py` 生成的参考也用同一套错误注入，导致"自测能过、
   真值不对"。

现在改为**精确解析式**（`App/control/gravity.c` + `App/cfg/gravity_model.h`）：

- 生成器 `Scripts/gen_gravity_model.py` 用与 `gravity_compensator.cpp` 完全
  相同的注入（`mass or 1.0`、`mc=first_moment`、夹爪 q=0），生成链常量；
- 运行期做 FK + `τ_k = −(R_k a_k)·Σ[(p_i−p_k)×(m_i g)+(R_i mc_i)×g] + offset`；
- Python 解析式 vs pinocchio `rnea`：**2.7e-14 N·m**；
- C（float）vs pinocchio（double）：**7.0e-5 N·m**（200 组随机位形）。

## 板端坐标映射（raw→q）——不能省 homing_offset

之前 `Gravity_TorqueRawF` 只做了 `q = direction·raw`，前提是"归零后
raw=0 即 q=0"。但模板机是**自然下垂归零**，raw=0 对应的是 q_hang，
不是 URDF q=0：实测肩 roll 约 ∓89.5°、腕 yaw 约 −57°，直接当 q=0 会差
**6 N·m 级**。

现在 `App/cfg/joint_map.h` 固化每关节的 `direction` / `homing_offset` /
关节区间（来自 `Scripts/model/calibration.yaml` + `joint_spec.yaml`，
`Scripts/gen_joint_map.py` 生成）：

```
q       = direction·(raw − homing_offset) + k·2π
τ_raw   = direction·τ_q
```

`k` 取"离关节区间中点最近的一圈"，抵消电机多圈。`Tests/test_gravity.c`
同时验证关节空间、raw 空间和 `raw+2π` 多圈三条路径。

⚠️ 换机器人 / 重新归零后必须重新生成 `joint_map.h`；`homing_offset` 是
模板机的值，跨台差异见 `DOCS/重力补偿移植说明.md` 的误差预算。

`App/cfg/gravity_fit.h` 与 `Scripts/fit_gravity.py` 已标记 DEPRECATED，
不再参与编译。详见 `DOCS/重力补偿移植说明.md`。
